# Tiemora Core v0.2.0 — planning (Sale / Pre-order / Orders)

Classification of `docs/flower-demo/core-feedback.md` and `docs/flower-demo/setup-log.md` into what
becomes Core v0.2, what stays demo-only, what is a Tiemora Studio candidate, and what still needs a
second demo before it is generalised. Written before implementation, per the v0.2 plan of record.

The two flower-demo documents named here belong to the separate Hana Hiên deployment and were never
part of Core; nothing in this repository resolves those paths. This page is kept as the historical
record of the v0.2.0 planning decisions.

## A. Core v0.2: generalised and taken in

- **Catalog**: `type` (`rental` / `sale`, inferred from the price key when omitted), `price.sale`,
  product `options` (group → choices, each an id or `{id, price}`), `addons`, `fulfillment`
  (pickup / delivery flags), `ordering` (`preorder`, `stock`, `deadline`), `category` as a list.
  Existing rental catalogs and products without a `type` keep their v0.1 behaviour exactly.
- **Orders domain**: `core/orders/rules.mjs` (statuses, transitions, pricing, date window, capacity,
  stock), `core/notifications/orders.mjs` (confirmation text, staff summary), `migrations/0006_orders.sql`
  (`orders`, `order_items`), `worker/orders.mjs` + `worker/orders-db.mjs` (public + admin API),
  `worker/customer.mjs` (contact validation shared with bookings).
- **Order statuses**: `pending → confirmed → preparing → ready → (out_for_delivery) → completed /
  cancelled`. Rental statuses are untouched and not unified with order statuses.
- **Fulfillment**: `pickup` and `delivery` only, as proven by the flower demo.
- **Capacity**: time slots with per-slot capacity, daily capacity, campaign window / rolling window,
  ordering deadline, per-product stock / sold-out. Configured generically under `ordering:`.
- **Store configuration**: `ordering:` section, `hero.eyebrow` / `hero.subtitle` / `hero.fit` /
  `hero.focus`, `logoStyle`, `store.text` copy overrides, theme tokens derived from `--primary` /
  `--accent` instead of hard-coded colours. Defaults stay industry-neutral (no florist wording).
- **Customer validation**: `worker/customer.mjs`, reused by both booking and order routes.
- **Notifications**: order confirmation text, order Web Push payload, preferred contact channel
  reuse, `contactDetails()` split out of `buildNotification`. No shared template engine yet.
- **Admin**: Orders list / detail / status transitions / schedule / customer notification helper,
  admin modules following the catalog's product types (no new registry abstraction).
- **Read-only demo mode** (`ADMIN_READ_ONLY`): generic OSS-demo feature, not florist-specific.
- **Theme / CSS**: semantic tokens (`--primary`, `--accent`, `--ok`, `--bad`) replacing the first
  store-specific hex literals found in `styles.css` / `admin.css`.
- **Examples**: `examples/sale/` (new, generic sample sale products) alongside the existing
  `examples/catalog/` (rental); `seed/sale-demo.sql` alongside `seed/demo.sql`.

## B. Demo-specific: stays out of Core

- Hana Hiên branding, name, tagline, hero copy, `store.text` overrides written for a florist.
- The 8 flower products, their photos, Vietnamese product copy, 20/10 campaign window and prices.
- `config/store.yaml`'s florist-specific `ordering:` values (20/10 dates, deadline, time slots,
  option/add-on catalog, message-card templates written for Mother's/Women's Day).
- `seed/demo.sql`'s florist orders, Hana Hiên logo/hero images, `wrangler.jsonc`'s flower-demo
  worker name and database id, `package.json`'s `hanahien-web` name.

## C. Tiemora Studio candidates (future GUI, not Core code)

- Store setup form, theme/logo/hero picker, campaign screen, product form with image upload/crop,
  ordering config editor (fulfillment, time slots, options, add-ons, card templates), copy presets
  per industry, one-click Cloudflare provisioning + secrets + deploy, sample-data generator.
- (`docs/flower-demo/setup-log.md`, "Tiemora Studio candidates" section, unchanged priority order.)

## D. Not yet generalised: needs Pho / Cafe / Workshop demo evidence first

- One unified `orders` model for rental + sale + workshop + appointment (`reservations` staying a
  rental-shaped `orders` for now).
- `capacity_overrides` table, staff/resource model, workshop seat model.
- A single `/api/availability?type=` endpoint replacing `/api/availability` + `/api/orders/config`.
- `preset: florist | rental | bakery | ...` config seeding `store.text` and `ordering` defaults.
- A shared notification-template-per-type table.
- `admin.modules` as an explicit, ordered registry (today: inferred from the catalog).
- `dine_in`, `on_site`, `rental_handover` fulfillment types; QR table order; generic capacity
  override DB; appointment staff/resource; workshop sessions.

These are deliberately left for the Pho Demo (local-food mobile order reusing the Orders domain),
the Cafe Demo (mixed-business store, admin module registry) and the Workshop Demo (on-site
fulfillment, seat/staff capacity).
