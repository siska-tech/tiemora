# v0.4.0 merge and upgrade notes

This release promotes rental workflows from the Omotenashi reference store into
Tiemora Core: timed rentals, fittings, turnaround, handoff hours, inventory timelines
and staff digests. Store-specific catalog data, branding and deployment bindings
remain in the store repository.

## Included

- Timed rentals use a pickup time and whole rental days. Optional per-product
  `price.additionalDay` reduces the price of additional days.
- Fittings hold inventory for the configured appointment and buffer, with no rental fee.
- Turnaround and actual return times determine inventory readiness. Overdue rentals
  continue to hold inventory according to the current turnaround policy.
- Weekly handoff windows, date exceptions and build-time public holiday calendars
  constrain pickup times. Fixed `booking.timeSlots` also work without a weekly schedule.
- Staff inventory timelines show bookings and care intervals. Timed candidate searches
  use the booking's time and purpose, so adjacent fittings remain editable.
- Customer confirmations include pickup/return times or fitting time and duration.
  Inventory readiness is not presented as the customer's return deadline.
- Optional staff digests use the store timezone, including delivery across midnight.
- Request deduplication includes pickup time, purpose and size. Closed days reject
  omitted pickup times, and display ticks no longer hide offset handoff slots.

See [booking](../booking.md), [configuration](../configuration.md) and
[inventory](../inventory.md) for the configuration and API contracts.

## Upgrade from v0.3.0

1. Record the current Worker version and back up the deployment database. Retain the
   store's config, catalog, secrets and Wrangler bindings; do not replace these with
   Core's example values.
2. Install the locked dependencies with `npm ci`. Run `npm run check` and
   `npm run deploy:check` using the intended deployment configuration.
3. Apply pending migrations **before deploying the new Worker**:

   ```sh
   npm run db:migrate
   ```

   For local development use `npm run db:migrate:local`. Core names the database
   `tiemora`; a downstream store must use its own configured database and scripts.

   | Migration | Change |
   | --- | --- |
   | `0010_booking_pickup_time.sql` | Adds the pickup time. |
   | `0011_rental_schedule.sql` | Adds rental duration, actual return and occupied moments, plus handoff exceptions. |
   | `0012_inventory_cleaning.sql` | Rebuilds inventory to allow `cleaning`, retaining items, assignments and indexes. |
   | `0013_fitting_visits.sql` | Adds booking purpose, defaulting existing rows to `rental`. |

   Use the migration runner's applied-migration history. A store that already applied
   these migrations does not need to execute their SQL again. The common bug fixes
   after the original rental patch introduce no additional migration.
4. Deploy the Worker and static assets together with `npm run deploy`. Timed rentals,
   fittings and digests require explicit store configuration. Existing untimed rows
   retain their whole-calendar-day occupied intervals, including when turnaround is enabled.
5. Check existing inventory, reservation assignments and order lines. Verify a new
   request and confirmation, adjacent fittings, editing a timed return date, handover
   and return, care-window availability, closed-day rejection and customer message times.
   If enabled, verify the digest target date and delivery on a subscribed test device.

Released migrations `0001` through `0009` are unchanged. The populated upgrade test
starts at `0009`, loads rental and sale demo records, applies `0010` through `0013`,
and verifies every pre-existing column, booking intervals, indexes, foreign keys and
database integrity. It runs on the SQLite D1 test adapter, not a production database.

If rollback is needed, retain the database backup and migration history. Do not drop
new columns/tables or replay the inventory rebuild as an improvised downgrade. Check
the older Worker's compatibility with newly created timed/fitting records before
switching versions; restoring a backup would discard subsequent writes.

## Validation

- `npm run check`: lint, typecheck, 233 tests and the standard build.
- `npm run build:pho-demo`: the isolated ordering demo still builds.
- `npm run deploy:check`: the standard Worker bundles successfully without deployment.
- `git diff --check`: no whitespace errors.

Windows validation uses `npm.cmd`. GitHub-hosted CI must also pass on the final PR
commit. Local validation does not independently verify a production deployment.

## Merge checklist

- Include the common fixes and regression tests in the committed PR diff.
- Keep `package.json` and the root lockfile version at `0.4.0`.
- Review the v0.4.0 changelog and upgrade notes with the release commit.
- Obtain a green CI run for that commit before merging and tagging the release.
